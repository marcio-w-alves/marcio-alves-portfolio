1. Overview

The portfolio (live at https://marciomariani.dev) is a Next.js site with an AI assistant that answers questions about Marcio's work, grounded in a typed knowledge base. Today it is English-only, its owner's data is scattered across src/core, src/app and src/ui (career facts are even repeated as literals in the fast-path answers), src/app mixes routes with loose helper files, and a code/content review done on 2026-10-28 found bugs, robustness gaps, content problems a recruiter would notice, and test/CI gaps.

This initiative makes the site bilingual (English + Brazilian Portuguese), turns it into a whitelabel template whose every owner-specific value lives in one profile folder, reorganises the code so reuse is structural rather than accidental, and fixes every finding of the review (except the "three names" finding, which the owner dropped). It is for two audiences: hiring managers and engineers who visit the site or open the repository, and a developer who forks it to run their own portfolio. It is scheduled now because the review is fresh and the next content pass (Portuguese résumé, product sites) would otherwise have to touch the same scattered literals twice.

2. Goals and non-goals

Goals

  • G1. Every visitor-facing string — interface, topic pages, fast-path answers, knowledge base, metadata, share image, résumé PDF — exists in English and Portuguese, selected by the URL.
  • G2. A fork can become someone else's portfolio by editing one profile folder (content + brand) and nothing else, verified by a test.
  • G3. src/app contains routes only; shared code lives in named modules; contracts shared by client and server have one definition.
  • G4. All confirmed bugs fixed, each with a regression test that fails without the fix.
  • G5. The record a recruiter reads is accurate and complete: headline, availability, current job first, no typos, overlapping roles explained, projects with real substance.
  • G6. The assistant's free-form answers are as grounded and relevant as the fast path's, measured by the local evaluation.
  • G7. The server survives abusive or long-lived traffic without unbounded memory, budget theft or hung streams.
  • G8. The README presents the project to a hiring manager or engineer.

Non-goals (explicitly out of scope)

  • NG1. The "three names" issue (Marcio Alves / marciomariani.dev / linkedin.com/in/marcio-montenegro). Names, domain and profile URLs stay exactly as they are.
  • NG2. Languages other than English and pt-BR; translated URL slugs (/pt/experiencia); right-to-left support.
  • NG3. Locale auto-detection, redirects, "view in Portuguese?" suggestions, or a remembered locale cookie. The URL alone decides.
  • NG4. Multiple profiles selected at runtime or by environment variable; a CMS; an admin UI.
  • NG5. Changing the set of seven topics per profile (the topics are fixed; their copy and questions are profile content).
  • NG6. Running pnpm eval:assistant in CI (owner decision: it stays local).
  • NG7. New Figma/HTML design artboards for Portuguese or for the new elements; Portuguese pages are not pixel-gated.
  • NG8. Request-time crawling of external sites; ingesting anything not on an explicit allow-list.
  • NG9. Translating /workbench, the fidelity specimens, /api error payloads meant for machines, logs, or tool contracts.
  • NG10. Persisting conversations beyond the browser tab (unchanged from today).
  • NG11. Showing the phone number on the website or letting the assistant disclose it (it appears only in the generated résumé PDF, as in the hand-made PDF today).

4. Functional requirements

Priority: M = must for this initiative, S = should. Every FR has acceptance criteria in §7.

A. Whitelabel profile

  • FR-1 (M) All owner-specific data lives in one profile folder: identity (name, first name, initials, headline, availability), contact links, domain-independent links (résumé path), the knowledge base in both languages, assistant identity, welcome copy, topic intros and questions, fast-path answer prose, interface copy, share-image text, site metadata copy, brand colours and fonts.
  • FR-2 (M) No file outside the profile folder contains an owner-identifying literal (name, first name, email, LinkedIn/GitHub URL or handle, domain, company names, metric values). A test enforces it.
  • FR-3 (M) Brand colours and font families come from the profile; the page tokens, the share image and the tab icon use the same values, with no second hand-kept copy.
  • FR-4 (M) Fast-path answers derive every fact (dates, companies, years, metrics, names) from the knowledge base; prose around those facts comes from profile copy. No career fact is a literal in src/core/assistant. Owner-specific intents and wording — e.g. the HRIS-lead answer, the Staff-scope answer, owner vocabulary such as "HRIS" or "UFPB" in the router — live in the profile; core intents carry generic names.
  • FR-5 (S) The profile folder carries a short guide (in the folder) listing what a reuser edits.
  • FR-54 (M) Core, server and UI unit/integration tests run against a fictional fixture profile (both locales, different name, colours, contact, roles, projects and answer copy); tests that use the real profile assert only generic properties (suggestion graph closes, integrity holds, index hash matches).
  • FR-55 (M) End-to-end tests read the expected visible text (name, headline, questions, labels) from the profile instead of hard-coding it.

B. Internationalisation

  • FR-6 (M) Every page exists at its English path and at /pt + the same path; both are prerendered. Any other path answers 404 with a page in the locale of its prefix.
  • FR-7 (M) Each page renders <html lang> as en or pt-BR and all visible copy in that locale, including topic pages, rich cards, empty/error/rate-limited states, aria labels and the 404/error pages.
  • FR-8 (M) A language switcher ("EN · PT") appears at the sidebar foot and in the phone drawer, links to the counterpart of the current page, marks the active locale, and is keyboard and screen-reader operable.
  • FR-9 (M) Conversations are held per locale and per page for the life of the tab (D5).
  • FR-56 (M) Portuguese is publicly reachable (routes, switcher, sitemap, hreflang) only once enabled in the profile, which happens at the end of the bilingual fast-path task (D30); until then /pt/* answers 404 and no surface links to it.
  • FR-57 (M) /en and /en/<page> redirect permanently (308) to the unprefixed URL (D31).
  • FR-10 (M) The fast path recognises the suggested questions and its intents in both languages on every page and answers in the question's language; ambiguous-language questions use the page locale.
  • FR-11 (M) The model path receives the page locale and replies in the question's language, using the page locale only to break ties.
  • FR-12 (M) Every suggested question and every follow-up offered by any answer, in both languages, is answered by the fast path (the suggestion-graph guarantee holds per locale).
  • FR-13 (M) The knowledge base exists in English and Portuguese with identical ids, dates, metric values and links; only text differs.
  • FR-14 (M) Retrieval searches passages of both languages and cites the same sources.
  • FR-15 (M) Per-locale metadata, hreflang alternates with x-default, sitemap entries for both locales, JSON-LD Person per locale, and a per-locale 1200×630 share image (D7).
  • FR-16 (M) Dates and numbers are formatted in the page locale (D27).

F. Assistant correctness and quality

  • FR-30 (M) The offer filter removes only closing offers of help and never a sentence that carries a fact (e.g. "If you ask about performance, he cut load time by 50%." survives).
  • FR-31 (M) The router answers or escalates — never refuses — "Did he act as a tech lead at Deel?", questions about "codebase health", "password reset flows" and "React children".
  • FR-32 (M) A request whose context carries an unknown or prototype-named intent (e.g. lastIntent: "constructor") is rejected at the boundary or treated as no context; it never throws.
  • FR-33 (M) Retrying or editing an older answer while another answer streams cancels the in-flight answer; no answer is left in a streaming state.
  • FR-34 (M) Model answers render links only to URLs that came from action results or the knowledge base; any other link is rendered as plain text.
  • FR-35 (M) Model answers to leadership/impact questions (in either language) cite the leadership facts of the record (Deel HRIS team lead, Roots team growth) and list as sources only records whose evidence the answer used.

G. Robustness

  • FR-36 (M) Rate-limit and budget maps evict entries whose window has passed, so memory is bounded by active clients, not by all clients ever seen.
  • FR-37 (M) Client keys normalise IPv6 addresses to their /64 prefix (IPv4 unchanged).
  • FR-38 (M) Tokens consumed by an answer that is interrupted (visitor leaves, error, timeout) are counted against the daily model budget.
  • FR-39 (M) The embeddings call has a timeout, honours the request's abort signal and sits behind a circuit breaker; an exception thrown by any tool's execution becomes a tool error the model sees, not a failed request.
  • FR-40 (M) GitHub and Wikipedia adapters validate the JSON they receive and log every failure (with status and cause) before degrading.
  • FR-41 (M) The chat stream sends a heartbeat at least every 15 s while waiting, and every request has an overall time limit (default 60 s, configurable) after which it ends with the interrupted event. The chat route's platform maxDuration is set above that limit (75 s), so the platform never ends the function first.

H. Architecture and organisation (behaviour-preserving)

  • FR-42 (M) src/app contains only Next.js route segments and special files; helpers (metadata builders, topic routing, workspace props, structured data, fonts, image fonts, brand colours) live in named modules outside it; the six topic pages share one implementation.
  • FR-43 (M) Boundary rules forbid: ui → infrastructure/composition-root/env; infrastructure → app/ui; app → infrastructure (except through the composition root); the rule that names a nonexistent components folder is corrected; server-only modules are guarded so importing them from a client component fails the build.
  • FR-44 (M) No package-level cycle between core/knowledge and core/assistant.
  • FR-45 (M) The client bundle does not contain the knowledge base: topic intros and records are built on the server and passed to the client as data; no client module imports the knowledge base.
  • FR-46 (M) Contracts used by both client and server — history turn, the interrupted error event, the event type list, the request schema, the question length limit — have exactly one definition, and the question length limit lives with the request policy.
  • FR-47 (S) Code-health fixes with no behaviour change: the model-assistant answer() split into single-purpose steps; the ChatWorkspace mapping extracted; one copy-confirmation timer shared by its two users; the conversation-store context value stable across renders; the temperature comment agrees with the value; next-intent and topic-default tables keyed by their union types; company patterns defined once.

5. Non-functional requirements

  • NFR-1 Performance. Lighthouse budgets in lighthouserc.json hold for / and /pt (perf ≥ 0.9, a11y 1, SEO 1, BP ≥ 0.95, LCP ≤ 3.5 s, TBT ≤ 300 ms, CLS ≤ 0.02). First-load client JS of / after FR-45 is at least 10% smaller than the baseline measured at the start of POR-59 (gzipped sum of same-origin scripts loaded by / on the production build), and no later task increases it by more than 5 KB gzipped (the switcher and catalogs included). Locale switching is a normal navigation to a prerendered page.
  • NFR-2 Accessibility. Zero axe WCAG 2.1 A/AA violations in the existing key states, in both locales. The switcher: native links, visible label, aria-current on the active locale, lang/hreflang on each link, ≥ 44×44 px target, focus-visible ring. Each page's lang matches its content.
  • NFR-3 SEO. Per FR-15; canonical points to the page's own locale; the e2e SEO spec covers both locales.
  • NFR-4 Fidelity. English boards keep ≥ 99.9% per board outside their element masks; masks cover at most 3% of a board; boards with layout changes carry a recorded departure (D26). Every mask and departure states its task and reason in scripts/fidelity/boards.ts. Tasks that must be pixel-neutral (the catalog and brand-token extraction) add no mask and no departure.
  • NFR-5 Security. CSP and headers unchanged; no new external origin at runtime (ingestion is offline); link allow-list per FR-34; no secret needed at build; ingestion respects robots.txt and the allow-list.
  • NFR-6 Resilience. Every new out-of-process call has a timeout; every synchronous dependency of a request is behind a circuit breaker (FR-39).
  • NFR-7 Architecture. src/core stays framework-free (dependency-cruiser passes with the FR-43 rules).
  • NFR-8 Translation integrity. A test fails if any EN catalog key or knowledge-base text field lacks a PT counterpart, or if ids/dates/metric values/URLs differ between locales.
  • NFR-9 Truthfulness. No task adds a fact not present in the résumé, the record, or an allow-listed site; Portuguese text is a translation, not a rewrite.
  • NFR-10 Delivery. One task = one PR titled POR-<nn>: <summary>, Portuguese non-technical body with online test steps; merges on green CI (owner authorisation). Every bug fix ships a regression test.

5.1 Catalog format and typing

  • Interfaces are owned by consumers (§4.2). EN and PT files are each typed : UiMessages / : SiteCopy / : AnswerSet.   • Copy functions are allowed only in server-side copy (answers.ts, site.ts, resume.ts), where prose wraps facts: intro: (k) => \${k.profile.firstName} is…\`. ui.ts` contains data only, because it crosses to the client.

8. Robustness designs

8.1 Bounded limiter and budget memory (FR-36, AC-36.1)

createSlidingWindowLimiter({ limit, windowMs, maxKeys = 50_000, now }):

  • On every admit, if at - lastSweep >= windowMs, iterate the map once and delete every key whose newest timestamp is <= at - windowMs. This is amortized O(1) per request, and memory is bounded by the clients active within one window.
  • Hard cap: if a new key would exceed maxKeys, evict the oldest-inserted key (Map iteration order). This protects against a key flood within a single window; log limiter.evicted once per sweep.
  • The model budget reuses the limiter, so it inherits both. Its daily counter is a scalar (already bounded).
  • Test: 10,000 distinct keys at t0, then one request at t0 + window + 1 → size() === 1. A size() accessor is exposed for tests and the health check.

8.2 Client key with IPv6 /64 (FR-37, AC-37.1)

  • http/client-key.ts#clientKey(raw: string): string:
    • trim; strip brackets, ports and zone ids (%eth0);
    • net.isIPv4 → as is;
    • IPv4-mapped (::ffff:a.b.c.d) → the IPv4;
    • net.isIPv6 → expand ::, take the first four hextets, emit xxxx:xxxx:xxxx:xxxx::/64;
    • anything else → 'unknown'.
  • clientIdOf(request) applies it to x-real-ip, then the first non-blank x-forwarded-for entry.
  • Tests: 2001:db8:1:2::a and 2001:db8:1:2::b give the same key; 2001:db8:1:3::a gives a different one; also compressed forms, mapped v4 and garbage.

8.3 Interrupted tokens (FR-38, AC-38.1)

  • OpenAI reports usage only in the final stream chunk (include_usage), so an aborted or failed round reports nothing today.
  • In core/assistant/system2, each round tracks sentChars (serialized messages + tool definitions) and receivedChars (text deltas + tool-call argument fragments).
  • In the round's finally, if no finish usage was observed, call onUsage(estimateUsage(sentChars, receivedChars)) with estimated: true. estimateTokens(chars) = Math.ceil(chars / 3) deliberately over-estimates (EN ≈ 4 chars/token, PT and JSON ≈ 3–3.5). The budget protects spend, so erring high is correct.
  • It is logged as model.usage_estimated. This covers visitor-left (generator return()), deadline, idle-timeout and provider errors.
  • AC-38.1 accepts "reduced by at least the tokens consumed (estimated)".

8.4 Embeddings: timeout, abort, breaker; tool exceptions (FR-39)

  • Ports:
    • EmbeddingPort.embed(texts, signal?);
    • KnowledgeSearchPort.search({ …, signal });
    • Tool.run(raw, signal?) and ToolRegistry.run(name, raw, signal?). The model assistant passes its request signal to every tool.
  • Adapter: client.embeddings.create(body, { signal: AbortSignal.any([signal, AbortSignal.timeout(EMBEDDINGS_TIMEOUT_MS = 4_000)]), maxRetries: 0 }). The answer is waiting on this call, so it does not retry.
  • Breaker: a separate instance (bulkhead: an embeddings outage must not open the chat-model circuit) with threshold 3 and a 30 s cooldown. circuit-breaker.ts gains guard<T>(breaker, call: () => Promise<T>): Promise<T>, next to the streaming withCircuitBreaker. Cancellation releases the breaker without counting a failure (same rule as today). /api/health reports retrieval: closed | open | half-open.
  • Tool exceptions: defineTool().run wraps execute in try/catch → { ok: false, error: 'The action failed: <tool-safe message>.' }, plus a call to the injected reportError (never the raw error text to the model). searchKnowledge turns CircuitOpenError or a timeout into { passages: [], note: 'Search is unavailable right now; answer only from other actions or decline.' }. Degradation therefore matches AC-39.1: the model answers without retrieval, and the fast path is unaffected.

8.5 GitHub and Wikipedia adapters (FR-40)

  • Zod schemas (userSchema, repositoriesSchema, summarySchema) live in the adapter. They are tolerant readers (.passthrough() is unnecessary; zod strips unknown keys by default).
  • On non-OK status, parse failure, timeout or network error, the adapter calls the injected report({ adapter, operation, status?, cause }) → logger.warn('adapter.degraded', …) and then returns the existing degraded null. The casts disappear.

8.6 SSE heartbeat and overall time limit (FR-41, AC-41.1)

  • http/event-stream.ts#eventStream(events, { heartbeatMs = 15_000, deadline: AbortSignal, reportError }):
    • pull() races iterator.next() against a heartbeat timer. Each tick enqueues the comment frame : keep-alive\n\n and re-arms, until next() settles.
    • When deadline aborts: iterator.return(), enqueue INTERRUPTED, close.
    • A generator error enqueues INTERRUPTED (as today).
    • cancel() returns the iterator.
  • chat-handler: const deadline = AbortSignal.timeout(settings.chatRequestTimeoutMs) (new CHAT_REQUEST_TIMEOUT_MS, default 60,000). The assistant receives AbortSignal.any([request.signal, deadline]), so model calls stop at the limit, and eventStream gets deadline so the visitor sees the interrupted event.
  • assistant.ts, when signal.aborted: if the deadline fired, rethrow so the stream emits INTERRUPTED; if the visitor left, end silently. The handler passes both signals: { visitor: request.signal, deadline }.
  • app/api/chat/route.ts: export const maxDuration = 75 (above the 60 s limit, so the platform never kills the function first). maxDuration is allowed under cacheComponents; only dynamic, revalidate, fetchCache and dynamicParams are not. POR-60 must verify this on a preview deploy.
  • Heartbeats reset the client's 30 s idle timer, because frames() calls onChunk() per read.

8.7 Client SSE parser (FR-48, AC-48.1)

The parser is extracted to ui/chat/sse-parser.ts: a pure createSseParser() with push(bytes): string[] and end(): string[], used by chat-client.ts.

  • TextDecoder with stream: true, and a final decoder.decode() flush in end() (a multi-byte character split across chunks).
  • Normalize \r\n and lone \r to \n. A trailing \r at a chunk end is held until the next chunk (CRLF split across chunks).
  • Frames split on a blank line. In end() the remaining buffer is parsed as a final frame (no trailing blank line).
  • Lines: data: strips one optional leading space (spec), and multiple data: lines join with \n. Comment lines (:) are ignored. event:, id: and retry: are ignored but tolerated.
  • Each of the four cases gets a test (AC-48.1), plus a heartbeat-only stream.

8.8 Link allow-list (FR-34, AC-34.1)

  • core/assistant/system2/link-filter.ts#createLinkFilter(isAllowed: (url) => boolean) is a streaming transformer with the offer filter's push/flush shape, chained after it.
  • It holds text from a [ until the matching ](…) closes, or until 2,048 chars or a newline arrive (then it releases the text as is).
  • A link whose URL is not allowed becomes its label alone. Bare https?:// URLs that are not allowed are kept as text: the UI's inline formatter does not auto-link, and a test pins that.
  • Allowed set: the knowledge base's URLs (contact, project links, repository, site-snapshot URLs), passed as knownUrls by the composition root; plus every URL in a tool result (the sources[].url and any https?:// string found by walking result.data), accumulated per answer.
  • URLs are compared normalized (new URL: protocol and host lower-cased, trailing slash dropped, hash dropped).
  • Defense in depth: the UI still refuses non-http(s)/mailto schemes.

1.2 Rules every test in this plan follows (owner's rules, made concrete)

  1. Test behaviour, not implementation. UI tests query by role, label or text: getByRole('link', { name: 'Português' }), not by class or by querySelector. Server tests assert the HTTP status, the SSE events, the logged line and the persisted map size, not which helper ran.
  2. Mock only at the boundary. The network goes through MSW (setupServer, onUnhandledRequest: 'error', so a stray request fails the test). Time goes through vi.useFakeTimers() or an injected now. The language model is mocked at the HTTP layer (MSW on api.openai.com) in route tests, and at the LanguageModelPort in core tests: it is the out-of-process port, never the unit under test. vi.mock is allowed only for next/navigation (third party) and the AC-46.1 constant override (§3, POR-58).
  3. No fixed sleeps. RTL uses findBy* and waitFor. Playwright uses web-first assertions, expect.poll and the existing holdNextAnswer gate. waitForTimeout is banned by test A-HYG (POR-62).
  4. E2E for critical journeys only (§5), at most 8 new or behaviour-changed spec files.
  5. Every bug fix (POR-41, 42, 43, 57) has a regression test that fails on today's main. The implementer proves it by committing the test first. The PR body shows the red run (test name and assertion message) before the fix and the green run after.
  6. No tautological or fabricated-state tests. A test may not set the value it then reads back. It may not assert only toHaveBeenCalled. It may not seed a store into the state the flow is supposed to produce. Each negative case (wrong input rejected) sits next to its positive.
  7. Every scanner proves it can fail. The whitelabel scan, the boundary rules, the client-reachability walk, the bundle scan, the hard-coded-copy check, the README check and the brand drift check each get a planted-violation self-test. A scanner that finds nothing on the real tree proves nothing until it has found something on a fixture.
  8. Names are behaviour sentences, e.g. keeps a factual sentence that starts like an offer, not isOffer works.

1.3 Owner-agnostic tests (D33, FR-54, FR-55)

  • Core, http, site and UI tests import @/testing/fixture-profile (§7.1). They assert the fixture's values ("Ada Rivera", "Acme").
  • Tests that need the real profile assert only generic properties: the suggestion graph closes, the index hash matches, the translations are complete, every topic question gets a fast-path answer, the roles are sorted. They contain no literals.
  • src/profile/profile.test.ts is the only test that names the owner. It holds the content assertions: D16, D17, D18, D19, D21, D22, the typos, and "Toptal is the current role".
  • E2E reads expected visible text from @/profile through e2e/support/profile.ts. Answer content is checked against profile data (knowledge fields and catalog questions), never by calling the fast path from the test. That would use the code under test as its own oracle.
