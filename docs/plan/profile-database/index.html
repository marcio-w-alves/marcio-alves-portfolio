1. Overview

The portfolio (live at https://marciomariani.dev, deployed on Vercel from a public GitHub repository) became whitelabel in i18n-whitelabel: everything about the owner lives in src/profile/**, and a fictional fixture profile ("Ada Rivera") proves a fork works. But "lives in one folder of a public repository" still means the owner's whole record — identity, contact, career, long-form notes, answer prose, evaluation cases, the embedded retrieval index, the photo and a résumé PDF carrying his phone number — is published in the repository and in its 297-commit history, along with tests and plan documents that name him.

This initiative moves all profile content into a Neon Postgres database that the site and the assistant read at build time only, and turns the repository into a generic template that ships only the fictional example profile plus the documentation to create, populate, publish and back up a profile database. Production keeps serving the owner's data with the same content and the same answers. Once production is verified on the database, the owner's data is deleted from the working tree and purged from the git history (rewritten and force-pushed; GitHub Support asked to purge cached pull-request refs). It is for the owner (privacy of his personal data), for visitors (nothing changes), and for a developer who forks the template (who gets a clean example and a documented path to their own database). It is scheduled now because the whitelabel boundary already exists, so the data has a single seam to move through.

2. Goals and non-goals

Goals

  • G1. After the purge, no file in the working tree and no object reachable from any branch, tag or notes ref of the repository contains the owner's profile data, checked by a scan over the full history.
  • G2. The database is the single copy of the owner's profile; the site, the assistant and every profile script read it, and the owner can edit, publish, back up and restore it without a code change.
  • G3. Production at https://marciomariani.dev serves the same pages and the same fast-path answers, byte-for-byte after normalisation, in every published locale, and the model path holds its evaluation pass rates.
  • G4. Visitors are never affected by the database: no request reads it; a database outage only blocks deploys.
  • G5. A fork, CI and local development build, test and run with the shipped example profile and no database credentials; a fork can follow the documentation to stand up its own database.
  • G6. The owner's data is never lost during the migration: it is loaded, verified and exported to a private local copy before anything is deleted.

Non-goals (explicitly out of scope)

  • NG1. An admin UI, CMS, web editor or any write path reachable from the site. The owner edits through local files and a command, or SQL.
  • NG2. Runtime reads of the database, on-demand revalidation, ISR or "edit goes live without a deploy". Publishing is "update the database, then redeploy" (D1).
  • NG3. A private repository (or any git repository) holding the owner's data. The database is the only copy; backups are database restore points plus local exports the owner keeps outside git (D2).
  • NG4. Several profiles served by one deployment, profile selection at request time, multi-tenancy.
  • NG5. Changing any content, copy, design, route, locale, URL or behaviour. This is a move, not a rewrite: the baseline comparison (FR-30) is the definition of "unchanged".
  • NG6. Generating the résumé PDF (POR-67 is dropped, D16). The current hand-made PDF moves as-is.
  • NG7. Purging copies outside this repository: forks (there are none today), clones on other machines, search-engine or archive caches, Vercel's private deployment history. They are recorded as residual risk (§8 Risks).
  • NG8. Rewriting pull-request titles, bodies, review comments or issue text on GitHub. PR history is kept (D11); FR-41 only reports which of them mention owner terms so the owner can decide by hand.
  • NG9. Hiding that the repository belongs to the owner's GitHub account. The account, the author name on commits and the live-site link in the README stay (D12).
  • NG10. Running pnpm eval:assistant in CI (unchanged: it stays local, now reading the database).
  • NG11. Adding font faces the template does not already bundle (see D19).

4. Functional requirements

Priority: M = must, S = should. Every FR has acceptance criteria in §7.

A. Profile store

  • FR-1 (M) The owner's whole profile (D3) is stored in a Neon Postgres database; nothing in D3 needs a file in the repository to build the owner's site.
  • FR-2 (M) The database has two access levels: a read-only credential used by builds (Vercel production and preview) and an owner credential that can write, used only on the owner's machine.
  • FR-3 (M) Every profile read from the database is validated with the same rules as today's validateProfile plus the generic checks (D17) before anything is built from it; an invalid profile fails with the path of every problem.
  • FR-4 (M) The database schema can be created from empty by one documented command, so a fork can stand up its own database.

B. Profile bundles: edit, import, export, backup

  • FR-5 (M) export writes the database's whole profile — text, binaries, index and embeddings — to a local directory as a profile bundle (D6).
  • FR-6 (M) import validates a bundle (FR-3) and, only if it is valid, replaces the database's profile with it in one transaction; an invalid bundle changes nothing and names every problem.
  • FR-7 (M) Before import changes anything it writes an export of the current database to a local backup location outside the repository, and reports where.
  • FR-8 (M) Export followed by import with no edit leaves the database identical; import followed by export reproduces the bundle's content identically.
  • FR-9 (M) Bundles, backups and any file holding owner data are written outside the repository by default, and the repository ignores the default locations, so they cannot be committed by accident.
  • FR-10 (M) The docs state the backup policy: the restore window of the Neon plan in use, how to restore to a point in time, how to restore from a local export, and how often to take a manual export.
  • FR-11 (S) A command reports what an import would change (added, changed, removed items per content type) without writing.

C. Build and scripts read the store

  • FR-12 (M) The production build prerenders every page from the profile read at build time; the assistant's API functions are deployed with the profile, index and embeddings of the same build. No request at runtime reads the database.
  • FR-13 (M) Profile selection at build follows D8: database when credentials exist; the example profile without them outside production or with an explicit opt-in; otherwise the build fails with a message naming the missing setting.
  • FR-14 (M) The PDF and the photo are served from the site's own origin at the URLs the profile names (production: /marcio-alves-resume.pdf, /marcio-alves.jpg), with the same bytes and content types as today.
  • FR-15 (M) pnpm rag:build and pnpm rag:probes read the corpus and probes from the selected profile and write the index and embeddings back to it (database or example bundle); the index-matches- corpus check holds for both.
  • FR-16 (M) pnpm notes:build and pnpm sites:ingest read their inputs from and write their outputs to the selected profile; the allow-list, robots and staleness rules are unchanged.
  • FR-17 (M) pnpm eval:assistant reads its cases and calibration from the selected profile.
  • FR-18 (M) One command triggers a production redeploy of the current main (the "publish" command), and reports the deployment it started.
  • FR-19 (M) Brand tokens (colours, font choice) and the generated stylesheet tokens come from the selected profile at build; no owner brand file is committed.

D. Answers and copy as data

  • FR-20 (M) Every fast-path answer, every topic page's copy, every follow-up, the router vocabulary, the interface overrides (ui, site), the about page and the global-error copy are data in the profile, per locale (D20).
  • FR-21 (M) Rendered from data, each answer and topic page is identical to what the current TypeScript copy produces for the same record, in every locale, for every intent, company, project and technology the record contains.
  • FR-22 (M) Answer templates name facts (companies, periods, metrics, counts, dates) only through placeholders resolved from the record; a template that states a figure the record does not hold, or references a fact that does not exist, fails validation with its path.
  • FR-23 (M) An answer or intent the profile's copy omits is not offered (as today: removing an owner intent's copy removes the answer, no core change).

E. Example profile and template documentation

  • FR-24 (M) The repository ships the example profile (D7) as a bundle; with no credentials, pnpm dev, pnpm build, pnpm test and pnpm test:e2e run against it.
  • FR-25 (M) The test suites (unit, integration, e2e) pass against the example profile and read expected visible text from the selected profile, never from a literal.
  • FR-26 (M) The documentation explains, in order: what a profile bundle contains (every content type and its rules), creating a Neon database and the two credentials, creating the schema, importing a bundle, building the index, publishing, editing, backing up and restoring, and the Vercel settings (env vars for production and preview, the redeploy command).
  • FR-27 (M) The README is a template's README (absorbs POR-70): what the project is, live example deployment link, stack, how it is built, how to make it yours (link to the profile docs), with setup detail in CONTRIBUTING.md.
  • FR-28 (S) ADRs record the build-time profile store (superseding ADR 0004's "committed index" for owner data) and the privacy boundary.

F. Migration and cutover

  • FR-29 (M) A baseline (D10) is captured from the build of main before any POR-88 change merges, stored outside the repository.
  • FR-30 (M) A comparison command builds the site from a given profile source and compares it to the baseline: every page, metadata output (titles, canonical, hreflang, sitemap, JSON-LD, share image), fast-path answer per suggested question and intent probe per locale, PDF and photo bytes, and probe retrieval results. It reports every difference after normalising build ids and hashes.
  • FR-31 (M) A one-time migration converts today's repository profile into an owner bundle (outside the repository), imports it into the owner's Neon database, and verifies it: round trip (FR-8), zero baseline differences (FR-30), and a local export the owner confirms he holds.
  • FR-32 (M) Cutover switches production and preview to the database (read-only credentials), deploys, and verifies production: zero baseline differences against the deployed site, /api/health reports the deployed commit, eval:assistant pass rates no lower than the baseline run, the publish command redeploys successfully.

G. Purge

  • FR-33 (M) After cutover is verified, every file in D15 is removed from the working tree or rewritten to be owner-free, and public/ holds no owner asset.
  • FR-34 (M) A privacy scan, given a profile's terms (identity, contact handles, domain, employers, products, schools, metric values, phone number, distinctive phrases of the notes), finds none of them in the working tree, and — in history mode — in any blob, path, commit message, tag message or notes ref reachable from any ref.
  • FR-35 (M) The privacy scan reads the owner's terms from the database or a local bundle, never from a committed file, and its output names file, line/commit and term kind, never the term itself, so it can run in public CI logs.
  • FR-36 (M) CI runs the working-tree privacy scan against the owner's terms on pushes and PRs from this repository (read-only credential as a CI secret, unavailable to fork PRs); a match fails the run.
  • FR-37 (M) History is rewritten (D11): owner paths removed from every commit, owner terms replaced in remaining blobs and commit/tag messages, author and committer emails rewritten to the noreply address (names kept), and every branch, tag and semantic-release notes ref force-pushed.
  • FR-38 (M) Every GitHub release points at its rewritten tag with notes regenerated from rewritten history, and the next semantic-release run continues the version sequence.
  • FR-39 (M) The repository and package.json are renamed to the neutral name (D13); Vercel's Git connection, the CI badge/links and the repo homepage still work after the rename.
  • FR-40 (M) A GitHub Support request to purge cached refs/pull/* and unreachable objects is filed with the rewritten-commit map, and its status is tracked in resume.md until GitHub confirms.
  • FR-41 (S) The purge report lists PR titles/bodies/comments and issue texts that contain owner terms (by number and kind only), for the owner to edit by hand if he chooses.

5. Non-functional requirements

  • NFR-1 Privacy. After D9: zero matches for the history-mode privacy scan (FR-34) across every ref of the remote; after GitHub Support confirms, refs/pull/* resolves only to rewritten commits. No owner data appears in public CI logs, committed fixtures, error messages or test snapshots at any time after D8. Owner bundles, backups and the baseline never enter git (FR-9).
  • NFR-2 Availability. No visitor request depends on the database (FR-12): with the database unreachable, every page, the fast path and the model path behave exactly as when it is reachable. A build that cannot read the database fails within 60 s of trying, naming the cause; the live deployment is untouched.
  • NFR-3 Build without credentials. pnpm build, pnpm verify and the CI jobs build, e2e, a11y and lhci run with no database credential and no network access to Neon, using the example profile. The CI build job still receives no secrets.
  • NFR-4 Performance. Lighthouse budgets in lighthouserc.json and the first-load JS budget hold unchanged on production; chat latency (time to first event) is unchanged because no request reads the database. Reading the profile adds at most 30 s to a production build.
  • NFR-5 Credential security. The database credentials are server/build-only environment variables, never NEXT_PUBLIC_*, never in the client bundle, never logged, never in an error message; connections require TLS. The build and CI hold only the read-only credential; the write credential exists only on the owner's machine. Rotating either credential is a documented procedure that needs no code change.
  • NFR-6 Resilience. Every database call made by the build and the scripts has a timeout and a bounded retry; an import is all-or-nothing (FR-6).
  • NFR-7 Cost. Added recurring cost US$0/month on Neon's free plan (D18); builds and deployments still never call the embeddings API.
  • NFR-8 Data integrity. No owner data is deleted from the repository until FR-31 and FR-32 have both passed and the owner holds a fresh local export (taken after cutover, before D8). The history rewrite runs only after a second export is taken and a bare mirror of the pre-rewrite repository is stored with it, outside git hosting.
  • NFR-9 Architecture. src/core stays framework-free; the database adapter sits outside the core and the composition roots; dependency-cruiser rules pass, with a rule that no page or route module imports the database adapter (it is a build-time dependency only).
  • NFR-10 Truthfulness. No content changes: every difference reported by FR-30 is a defect, not an edit, unless the owner accepts it in writing in the PR.

6. Use cases

UC-1 Owner edits and publishes his profile

  • Scope: profile store and its commands · Level: user-goal · Primary actor: owner
  • Stakeholders: owner (change one answer or fact safely); visitors (see the updated site).
  • Preconditions: owner credential on his machine; the database holds a valid profile.
  • Success end: the site serves the edited content; a pre-import backup exists locally.
  • Trigger: the owner wants to change a fact, a translation or an answer's wording.

Main success scenario:

  1. Owner exports the profile to a local bundle.
  2. Owner edits the text files of the bundle.
  3. Owner asks for a preview of changes; System lists what would change per content type.
  4. Owner imports the bundle; System writes a backup export, validates the bundle and replaces the profile in one transaction.
  5. Owner rebuilds the retrieval index; System writes the new index to the database.
  6. Owner runs the publish command; System starts a production redeploy and reports it.
  7. System builds from the database and the edited content goes live.

Extensions:

  • 4a. The bundle is invalid (a translation adds a figure, a template names a missing fact): System changes nothing and lists every problem by path.
  • 5a. Owner skips the rebuild: the build fails because the index does not match the corpus.
  • 6a. The database is unreachable at build: the deployment fails naming the cause; the previous one stays live.
  • *a. Owner made a mistake already published: Owner imports the backup export (or restores a point in time) and publishes again.

UC-2 Visitor gets the same answers

  • Primary actor: visitor (recruiter, engineer) · Goal: learn about the owner.
  • Main success scenario:
    1. Visitor opens any page in any published locale.
    2. System serves the prerendered page, identical to before the migration.
    3. Visitor asks a suggested question; System answers from the fast path with the same answer as before.
    4. Visitor asks a free-form question; System answers through the model with the same grounding.
    5. Visitor downloads the résumé at its usual URL.
  • Extensions: *a. The database is down: nothing in 1–5 changes.

UC-3 Fork sets up their own profile

  • Primary actor: developer who forked the template · Goal: run their own portfolio.
  • Main success scenario:
    1. Developer clones the fork and runs it; System serves the example profile with no setup.
    2. Developer creates a Neon database and the two credentials, following the docs.
    3. Developer creates the schema and imports a copy of the example bundle edited with their data.
    4. Developer builds their index and sets the read-only credential on Vercel.
    5. Developer deploys; System builds every page, answer, asset and metadata from their database.
  • Extensions: 3a. Their bundle is invalid: System names every problem. 5a. They deploy to production without credentials: the build fails and names the setting, or serves the example if they opted in.

UC-4 CI runs with the example profile

  • Primary actor: CI (GitHub Actions) · Goal: gate a change without any owner data.
  • Main success scenario:
    1. A push or PR runs the CI jobs with no database credential.
    2. System builds, tests and runs the browser checks against the example profile.
    3. On this repository's own pushes and PRs, the privacy job reads the owner's terms with the read-only secret and scans the working tree.
    4. System reports green.
  • Extensions: 3a. A change re-introduces an owner term: the privacy job fails naming file, line and term kind. 3b. A PR comes from a fork: the privacy job has no secret and is skipped; the owner re-runs it on merge to main.

UC-5 Owner migrates, cuts over and purges

  • Level: summary · Primary actor: owner, with the orchestrator · Goal: data only in the database.
  • Main success scenario:
    1. Orchestrator captures the baseline from main (kept outside git).
    2. The template learns to read profiles from bundles and the database (D1–D5 deliverables).
    3. Migration loads today's profile into Neon and verifies it against the baseline; owner holds an export.
    4. Cutover switches production to the database; production matches the baseline.
    5. Owner takes a fresh export; owner data is removed from the working tree.
    6. Owner takes a final export and a mirror; history is rewritten and force-pushed; releases are re-pointed; the repo is renamed; GitHub Support is asked to purge.
    7. History scan finds nothing; production still matches the baseline.
  • Extensions: 3a / 4a. Any baseline difference: stop; nothing is deleted until it is resolved. 6a. A stray branch or open PR exists: stop until it is merged or closed. 6b. Support has not confirmed: recorded as residual risk, tracked in resume.md.

2. Architecture and target structure

2.1 Bounded contexts and dependency direction

Two contexts meet at one Published Language:

  • Profile authoring & publishing (tooling, scripts/profile/**): bundles, the store, revisions, import/export/diff, checks, materialization, publish. Its model: _ProfileBundle_ (a set of _documents_), _Revision_, _Head_, _Workspace_ (where a script reads and writes: a bundle directory or the database).
  • The site (src/**): reads a _Materialized profile_ — JSON plus assets on disk — and never knows where it came from.

The _Materialized profile_ (src/profile/generated/*, schema in src/profile/schema.ts) is the contract between them. Tooling imports the contract from src; src never imports tooling.

Rules enforced by bundle/read-directory.ts and the import (each violation names the path):

  • Only paths in the layout; dotfiles are ignored (macOS .DS_Store); symlinks are refused; path segments match [A-Za-z0-9][A-Za-z0-9._-]*.
  • Text documents are UTF-8 without BOM and without CR (a CRLF template would render \r\n and break equivalence); the error says "save with LF line endings".

strict: true, maxAliasCount: 100 } — no implicit yes/no` booleans, no duplicate keys, no alias bombs.

The bundle format version (format) is checked on decode; code supports exactly its current version. The first breaking format change ships an upgrade command that rewrites a workspace into a new revision; additive changes do not bump it (tolerant reader).

3.3 Integrity, reads and writes

  • Manifest and digest. `manifest = join('\n', sort_bytewise(paths).map(p => p + '\t' + mediaType +

'\t' + hex(sha256(bytes)))); digest = sha256(utf8(manifest)). SQL sorts with collate "C"` so both sides agree. Equal digest ⇒ identical profile, which makes import idempotent and FR-8 checkable.

  • Build read (reader role, one round trip each, in begin isolation level repeatable read read only): select r.id, r.digest, r.bundle_format from profile.head h join profile.revision r on r.id = h.revision_id then `select d.path, d.media_type, b.bytes from profile.document d join profile.blob b on b.sha256 =

d.blob_sha256 where d.revision_id = $1 order by d.path. The client re-hashes every blob and the manifest; a mismatch fails the build ("stored profile is corrupt") rather than shipping it. An empty head` fails with "the database holds no profile yet — import a bundle".

  • Import / write (owner role), one transaction, isolation level serializable:
    1. insert into profile.blob … on conflict (sha256) do nothing for each new blob;
    2. insert the revision (digest, format, origin, note) and its documents;
    3. update profile.head set revision_id = $new, updated_at = now() where revision_id = $expected (insert on first import). 0 rows ⇒ abort: someone wrote since the backup was taken ("the profile changed since your backup; run the import again").
    4. Commit. A crash or a timeout before commit leaves the previous head (AC-6.2).
  • Retention (Steady State). After a successful write, a separate transaction keeps the newest 20 revisions plus head and deletes orphan blobs. Twenty revisions of a few MB with dedup stay far below the free plan's storage.
  • Restore inside the DB: pnpm profile restore <revision> writes a _new_ revision whose documents equal the old one (origin restore), so history stays append-only.

Reads retry 3 attempts, exponential backoff with full jitter (base 1 s, cap 8 s), only on connection errors (ECONNREFUSED, ETIMEDOUT, ENOTFOUND excluded — it is a config error — SQLSTATE class 08, 57P01, 57P03). A circuit breaker is deliberately absent: there is no long-running caller to protect — each CLI run makes at most three attempts and exits, which is the breaker's open state.

Error messages name host, operation, attempt count and SQLSTATE, never the URL or a credential; the URL is parsed once and never interpolated into a message or log line.

10.2 Modes and output

  • History (--history <clone>): git rev-list --objects --all (paths and blobs), blobs streamed through git cat-file --batch, commit messages, tag messages, notes refs. Reports blob <id> <path>:<line>, commit <id> message, path <id> (the path itself matches).

1.2 Rules every test in this plan follows (owner's rules, made concrete)

  1. Test behaviour through the public surface. Tooling tests run pnpm profile <command> (or the script) as a child process and assert its exit code, its output, the files it wrote and the rows in the database. Core tests call compileLocaleCopy and the chat handler, not private render helpers.
  2. Store tests never mock the database. Each *.store.test.ts file creates its own database (profile_test_<random>) through the admin URL, runs the real pnpm profile init and drops it in afterAll. The store project fails (never skips) when PROFILE_TEST_ADMIN_URL is unset. No in-process fake of pg; the in-memory ProfileWorkspace is allowed only in U tests of use-case logic (diff grouping, digest), never as evidence for an AC that names the database.
  3. Mock only at the network boundary. MSW with onUnhandledRequest: 'error'. Git is never mocked: the publish and history tests use real temporary repositories (git init --bare as origin).
  4. No fixed sleeps. Waits are conditions: poll pg_stat_activity until the session under test is wait_event_type = 'Lock'; Playwright web-first assertions; fake timers for publish polling and retry backoff (injected sleep/now). Wall-clock is measured only where the AC is a time bound (AC-13.2).
  5. Every scanner and every check proves it can fail. Each check of §4.2 of the design, the privacy scan, the dependency rule, the artifact scans and the equivalence oracle get a planted-fault twin. A check that passes on the real tree proves nothing on its own.
  6. No fabricated state. A test may not insert the head pointer it then reads, may not hand-write manifest.json to test the next step (it runs materialize), and may not seed the result of the command it tests. Faults are planted in inputs (a bundle file, a SQL profile.revise, a lock held by another session), never in the code path.
  7. Credentials never leak through a test. A shared expectNoCredential(output, url) helper asserts that stdout and stderr of every failing store/publish command contain neither the URL, the password, nor the token. It is called in every S and publish test that exercises an error path.
  8. Names are behaviour sentences, e.g. an interrupted import leaves the previous profile at head.
